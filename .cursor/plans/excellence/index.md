> 2026-09-26 起，本目录不再是第二条总任务。调度以 [工程手册的整项目优化路线](../../../docs/engineering.md#整项目优化路线) 为准；这里只跑该路线的 W3–W7。

## 0. 使用方法（给用户）
1. **R0a、R0b 手动跑**：新开对话输入 `@.cursor/plans/excellence/R0a-execute.md 按这个文件执行`。它汇报后，再新开对话输入 `@.cursor/plans/excellence/R0a-verify.md 按这个文件验收`。不通过就再新开对话：`@.cursor/plans/excellence/R0a-execute.md 这是原任务；只修下面的整改清单，修完重跑「最终验证」：<粘贴整改清单>`，然后重新验收。R0b 同理，必须在 R0a 验收通过之后。
2. **S0 用批量执行器跑**（在仓库根目录的终端里）：
   - 试点：`python3 .cursor/plans/excellence/tools/run.py audit --ids S0-001 S0-002 S0-003 S0-004`，然后 `python3 .cursor/plans/excellence/tools/run.py verify --batches V01`，再 `python3 .cursor/plans/excellence/tools/run.py status`。
   - 试点跑完，新开对话：`@.cursor/plans/excellence/architect.md S0 试点跑完，请复盘`。架构师确认后再全量：`run.py audit`、`run.py verify`；status 里列出的待整改单元跑 `run.py fix --ids …`，再对相应批次跑 `run.py verify --batches Vxx --force`，直到全部通过。
3. **之后每个阶段**：新开对话 `@.cursor/plans/excellence/architect.md <阶段> 验收通过，出下一份`。执行和验收永远是两个不同的新对话。

## 1. 目标
把 AreaChain 做成拿出去能评为优秀的项目，并且「高度自理」：
- 职责自洽：每个类型只管一件事，界面里不藏业务规则。
- 规则自动守：约定落成测试和 `scripts/check_workflow.py` 检查，不靠人记。
- 结构自解释：新人不问作者，靠文档和代码就能接手。

## 2. 原则
- 面向对象按 Swift 惯用法：封装、抽象、多态、组合。抽象用 `protocol`，值用 `struct` / `enum`，`class` 只用于需要身份或共享状态处（SwiftData 模型、可观察状态）。不建继承树。
- 模式必须对应真实问题：需要替换实现或隔离测试才抽协议；只有一个实现时不加接口、工厂。架构文档里要有模式清单：位置、解决的问题、为什么不用更简单的写法。
- 单一来源：每个决定只放在一个地方（值 → 令牌；结构与交互 → 基座和布局组件；规则 → Domain / Services 的唯一入口；文案 → `Localizable.xcstrings`），改一处全局生效；新功能只做组合。
- 有意的差异保留为具名 variant，不抹平（剪贴板保留原文、搜索不建标签、`workspaceEmbedded` 只表达能力差异等，见 `AGENTS.md`）。
- 重构只改结构、不改行为；基座要有自己的测试，并能列出消费者。
- 评审口径：业内代码评审（写法地道、测试到位、文档有模式清单）。

## 3. 执行约束（用户定）
- 在 Claude Code 里执行；每份提示词在一个对话内完成。
- 每个对话新增内容不超过 16k tokens（不含系统提示、工具定义、自动加载的规则等固定开销）。中转站上下文一长就会延迟、报错。
- 所以提示词必须自包含，控制在 7KB 左右；每单元读取不超过 700 行；命令输出截断；结果写文件，对话只回几行；不派子代理；超预算就停下并记录剩余部分。
- 同类任务用「一个模板 + 一张单元表」。批量阶段由 `tools/run.py` 用 `claude -p` 逐个新会话执行：`env -i` 干净环境、不用 `--bare`、`--strict-mcp-config`、不传 `--model`（保持用户设定的模型）、`--effort` 默认 `medium`（试点后按实测调整）、`--permission-mode dontAsk` 加最小白名单。
- 本机 `python3` 是 3.9.6、`claude` 是 2.1.280：脚本和提示词里的命令都按这两个版本写，不用 3.10 以上的 Python 写法。

## 4. 角色与流程
- 架构师：只生成提示词和计划文件，不改代码。当前对话结束后，用 `architect.md` 在新对话接力。
- 执行（A）→ 独立验收（B，新对话）→ 不通过则开 C，只修整改清单，修完再跑 B。执行者与验收者不共用上下文。
- 批量阶段的执行与验收都由 `run.py` 各开新会话；不通过的单元用 `run.py fix` 整改后重验。
- 需要用户定的取舍：执行对话停下提问，复述确认后写进 `log.md`，架构师再收进本文件的决策记录。

## 5. 闭环规则（吸取 design-system 计划的教训）
1. 绑定：验收稿第一步核对启动指令里的文件名；记录行写明所用提示词文件名。
2. 回写：阶段收窄或改变规格时，架构师在同一步更新本文件；执行者只能在 `log.md` 标「待回写」。
3. 人工步骤写明谁做、结果记在哪里；没有记录不能勾选。
4. 命令先试跑：提示词里的检查命令由架构师在当前代码上试跑过，实际输出写进提示词作为预期。
5. 自审：每份提示词交付前逐字自审（路径存在、行号属实、命令可跑、预算估算、绑定正确），并更新 `MANIFEST.sha256`。
6. 防篡改：执行与验收都跑 `shasum -a 256 -c --quiet .cursor/plans/excellence/MANIFEST.sha256`；清单里的文件只有架构师能改。
7. 沉淀：只把重复出现、证据明确的问题沉淀成检查或规则。
